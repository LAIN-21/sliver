# Architecture

This document records system-level decisions, assumptions, and open questions. Product invariants live in [PRODUCT.md](PRODUCT.md).

## Decisions

- Sliver does not make autonomous buyer spending decisions.
- Resource is a first-class domain abstraction.
- A Resource is a purchasable view over an underlying data source.
- Protected underlying data must not leak through discovery metadata.
- Seller, marketplace/catalog, buyer-facing interface, and transaction layer are distinct conceptual responsibilities.
- Those four conceptual responsibilities are an agreed architectural decision. They are not automatic microservices, packages, modules, or deployables.
- The old `ripple-challenge` Ledger402 autonomous procurement agent is a reference/demo buyer, not the Sliver architecture.
- Initial work focuses on structured dataset sellers.
- Enterprise API integration should eventually converge into the same marketplace abstraction.
- Sliver is intended to support settlement through the XRP Ledger.
- The API and pipeline worker use Python 3.13, FastAPI 0.115.x, SQLAlchemy 2 and Alembic; the web app uses React, TypeScript, Vite and Tailwind CSS. See [ADR 0003](adr/0003-application-stack-and-local-containers.md).
- Local development runs entirely in Docker Compose: PostgreSQL, MinIO, API, worker and web, published on 127.0.0.1 only.
- Background jobs are PostgreSQL rows claimed with `FOR UPDATE SKIP LOCKED`; there is no queue service. Each seller upload gets one `pipeline_steps` row per stage. A step is claimable once every earlier step of its dataset has finished, so a dataset's stages run in order while several workers can serve different datasets. A step left `running` by a dead worker is reclaimed after a timeout (five minutes by default) and fails after three attempts.
- The seller inspection pipeline is an ordered stage registry (`pipeline/registry.py`): validate, profile, privacy, duplicates, ai_review, research, package, decide. Each stage returns findings with a severity (`high`, `medium`, `low`); any `high` finding fails the stage. Stages read the database and return results; only `jobs.finish` writes them, including the Resources `package` creates. A failed validation skips the remaining stages and rejects the dataset. Otherwise every stage runs and `decide` applies deterministic rules: blocking findings (any `high`, a stage that did not finish, `medium` privacy or near-duplicate findings, a `medium` sensitivity concern from the AI review) send the dataset to the reviewer queue (`review`); without them, a quality score at or above `SLIVER_AUTO_ACCEPT_QUALITY` accepts it (`accepted`, ready for pricing), and a lower score also goes to the queue. Reviewers approve or reject queued datasets with a reason. Accepted datasets are then valued and published by their seller (below). See [agents/seller.md](agents/seller.md).
- The AI review calls the Claude API (`sliver_api/ai.py`, model from `SLIVER_AI_MODEL`) with structured output through a strict tool call and versioned prompts in `sliver_api/prompts/`. Only the column schema, the column profile and at most 20 sample rows leave Sliver, with cells the privacy scan flagged redacted; research (behind `SLIVER_AI_RESEARCH`) sends only the public listing and schema and uses Claude's web search. Answers are cached in the private bucket by prompt version, model and dataset SHA-256. Without `ANTHROPIC_API_KEY` a deterministic fallback writes the listing, so the pipeline never depends on the API. Model output informs metadata and slicing only; it can send a dataset to a reviewer but never accept one.
- `package` materializes the full dataset and one Resource per value of a category column (or per calendar month of a date column) with the slicing code shared with the demo seed (`sliver_api/slicing.py`). Each sliver is its own immutable CSV object with its own SHA-256, created as a `draft` (or `review`) Resource with a placeholder price of 1 cent until the seller publishes it. A leak guard (`pipeline/leakguard.py`) rejects public titles, descriptions, tags and categories that contain raw cell values of any column other than dates and low-cardinality, non-personal category columns.
- Valuation (`sliver_api/valuation.py`) is a pure, deterministic function: suggested price = base × quality × uniqueness × demand × public availability × coverage, rounded to whole cents and clamped to the `resources.price_minor` bounds (1 cent to $1,000,000). The base is the median price of at least two published slivers in the same category (other datasets only), otherwise a fixed category base. Quality maps the acceptance score (0-100) to 0.5-1.0; uniqueness is 1 − 0.6 × the largest row overlap the duplicates stage measured against the seller's own and published data; demand adds 10% per unmet catalog search whose terms the sliver's public text mostly covers (at most +50%, last 30 days); public availability is 0.5 when research found a free equivalent, 0.75 for a partial one and neutral when research did not run or could not tell; coverage is √(rows ÷ the comparables' median rows, or 1,000), bounded to 0.25-4. The range is ±20% around the suggestion with comparables and ±35% without. Each factor is rounded before multiplying and returned with its inputs and reason, so the breakdown multiplies out to the price. Claude only writes the plain-language explanation (`prompts/valuation_explanation.v1`) from the computed numbers and short reasons; it never sees rows, cell values or search texts, and an answer containing a number that is not in its input is replaced by a deterministic template, as is any answer when there is no key or the call fails. Publishing never calls Claude: it reuses a cached explanation of the same numbers or the template.
- Sellers publish their own accepted (or reviewer-approved) datasets: every draft sliver at its suggested price or the seller's override within the price bounds, together, with a private snapshot of the valuation (inputs, breakdown, price, explanation) on each Resource. Repricing after publication is not supported. Sample rows stay private unless the seller selects them (at most five); rows holding a value in a privacy-flagged column, or any value a privacy detector matches, are refused. Selected rows are copied onto each published sliver they belong to (`resources.sample_rows`) and are the only row content public discovery ever shows. Published slivers are sold through the unchanged x402 path.
- Sellers see unmet demand and their own earnings (delivered purchases with Testnet explorer links; gross, Sliver's fee and net per sale and in total; the fee owed to Sliver) at `/sell/insights`. The page follows the public activity stream and reloads when one of the seller's slivers is delivered.
- Sliver's platform fee is recorded, not collected ([ADR 0005](adr/0005-platform-fee-model.md)). The buyer pays the full price to the seller on-chain, and the x402 path is unchanged. When a payment becomes `delivered`, the same commit snapshots the fee rate (`SLIVER_PLATFORM_FEE_BPS`, default 1000 = 10%, bounded 0–5000), Sliver's fee and the seller's net on the payment row, in drops and USD cents (`payments/fees.py`). The fee is rounded down to a whole drop and a whole cent, so the net is the remainder and fee + net = gross exactly. A recorded fee is never replaced, so rate changes affect only later sales. Payments delivered before migration `0008_platform_fee` keep NULL fee columns ("no fee recorded"). Fees are settled with sellers off-chain; there is no invoicing or settlement tracking yet. The public receipt and purchase timeline state the split through `activity/public.py` (`public_fee`). Activity events do not carry it.
- Seller uploads are stored once under a new key with their SHA-256 and never overwritten; the worker re-checks the hash before every stage.
- Sellers and reviewers are demo accounts with scrypt password hashes set from the environment by `make seed` (there is no public signup). Sign-in creates a server-side session; the browser holds only a random token in an `HttpOnly`, `SameSite=Lax` cookie, and the database stores its SHA-256. Every mutation must carry an allow-listed `Origin` header.
- A Resource ("sliver") is either a whole dataset or one slice of it (one value of a column, or one calendar month of a date column). Each Resource is stored as its own immutable CSV object with its own SHA-256, so delivery and integrity checks never touch the rest of the dataset.
- Public discovery serializes Resources through one allow-list (`catalog/public.py`) and searches them with PostgreSQL full-text search, matching any query term and ranking by relevance. The only row content it exposes is sample rows the seller explicitly selected. See [agents/catalog.md](agents/catalog.md).
- Resources are bought with x402 v2 on XRPL Testnet: `GET /api/resources/{id}/data` answers 402, buyers pay the seller directly with a presigned Payment, a facilitator (t54 by default) settles it, and Sliver independently checks the ledger before delivering. Sliver never signs or holds funds. See [ADR 0004](adr/0004-x402-payments-on-xrpl.md) and [agents/transactions.md](agents/transactions.md).
- The buyer-facing interface is an open-source stdio MCP server (`packages/sliver-mcp`) that runs on the buyer's machine with the buyer's own XRPL Testnet wallet. It evaluates fit, enforces the buyer's local budget and caps, checks every 402 challenge against the listing before signing, and verifies the delivered SHA-256. It signs with `packages/sliver-x402`, a small x402 client of our own, because the `x402-xrpl` SDK's `uvicorn<0.31` pin conflicts with the `mcp` SDK. Sliver hosts no buyer agent and holds no buyer keys.
- Every purchase step (402 issued, signature received, verified or rejected, integrity checked, settlement submitted, settled, validated on the ledger, delivered, pending, failed) is appended to `activity_events` in its own short transaction, outside the purchase's transaction and locks, so recording never changes payment behaviour. The table has no foreign key to `payments` on purpose (a child insert would wait on the invoice row the purchase holds `FOR UPDATE`). Events are public: they serialize through one allow-list (`activity/public.py`) and never hold payment headers, signed blobs, invoice ids or other buyer secrets. The web app reads them from `GET /api/activity`, `GET /api/purchases/{id}` and a server-sent events stream (`GET /api/activity/stream`) that polls the table every 0.5 s and resumes from `Last-Event-ID`; writers serialize on an advisory lock so event ids become visible in order.
- Every text search of the catalog (first page) records an anonymous search event. Searches whose text matched nothing are exposed as unmet demand (`GET /api/demand`) for sellers.

## Current assumptions

- Seller uploads are UTF-8 CSV only. JSON and Parquet are possible later source formats; neither is supported.
- The valuation constants (category bases, factor weights, demand window) are demo calibrations, not market research.
- Prices are set in USD and converted to XRP drops at a fixed, disclosed demo rate (`DROPS_PER_USD`, default 400,000 drops per USD, see [ADR 0004](adr/0004-x402-payments-on-xrpl.md)). The rate is illustrative, not a market price.

## Open questions

- Cloud provider
- Cache
- Vector database
- Authentication provider beyond the demo accounts
- Resource metadata schema
- Calibrating the pricing formula against real sales
- Whether the four conceptual responsibilities become packages, modules, services, or deployables
- Settling the platform fee on-chain (an XRPL Batch split, see [ADR 0005](adr/0005-platform-fee-model.md)), fee invoicing, payouts beyond direct payment, refunds, and mainnet operation
